# 0119 重新打包的验证者持 owner 心跳租约，等待器据此证明它已不在

- 日期：2026-11-09
- 状态：accepted
- 来源：台账 TD-337、TD-345；第 91 批。方案先经 kimi 方案审查（REVISE），采用它提出的较小方案。
- 关系：扩展 0096 的验证者缺席证明，多覆盖一种形状；0096 的 completed 形状不变。

## 背景

1. MCP `run_delivery_repackage` 在一次请求里打包并验证。有界等待 300 秒，比宿主约 60 秒的请求上限长，宿主先报超时，打包其实已经成功。
2. 验证跑在 MCP 服务进程里。2026-11-05 宿主换掉 MCP 服务时验证跟着没了，交付停在 verification pending。
3. 0096 的证明只认终态 completed 的后台运行（验证者是 runner）。终态 failed、交付来自重新打包的运行拒于 `not_pending`，`runs wait --until-settled` 一直等。

## 决定

1. 有界等待缺省 45 秒（`WAO_DELIVERY_WAIT_MS` 覆写不变），repackage 与 reverify 共用；超窗回执如实说验证在这个 MCP 服务进程里。
2. 重新打包的验证期间（进验证闸前到结果落盘），调用方持本运行的 owner 心跳租约 `.owner-<runId>`，与 runner 同一套写法：原子替换写、每 2 秒续写、只删 pid 是自己的租约；同一进程里同一运行的多个持有者，最后一个停下才释放。
3. 验证者缺席证明多认一种形状：终态 failed、最后一条绑定的 state_change 到 failed、created 带有效的重新打包来源、验证显式 pending、无结果、无 reverify。这一形状不要求后台派发、不拒 rerun、不过 daemon 门（daemon 不碰终态运行），扫描的时间锚取 created；租约门、静默窗门照旧。
4. 证明成立时 nextStep 指以相同输入再调 `run_delivery_repackage`（已有 created 时不重新打包，只重跑验证），或趁 pending 拒收。

## 被否方案

- **后台验证进程**（repackage 受理即返回，验证交给有心跳租约的独立进程）：MCP 服务被换掉后验证能自己接着跑，但要一套跨进程只起一个验证者的认领协议、起进程失败的语义和启动交接；这种情形至今只出过一次，Lead 再调一次 repackage 就能续上。
- **只把有界等待降到 45 秒**：宿主不再先超时，但服务进程没了等待器仍一直等。

## 已知局限

- MCP 服务被换掉后验证不会自己续跑，要 Lead 再调一次 repackage。
- 等待器要等最后一条绑定事件满 15 分钟静默窗才可能给出 verifier_gone。
- 验证者是 MCP 服务，命令行不带 runId，进程扫描认不出它；这一形状的存活证据只有租约。扫描门仍会因"晚于时间锚创建、读不到命令行的 node 进程"拒绝，时间锚越早越容易拒。
- 合入前已在跑的 MCP 服务用旧代码验证，不写租约；新等待器可能在它还在验证时判它已不在，Lead 照提示再调一次就会多跑一遍验证（结果写入是 CAS，只落一条）。合入后重启各宿主的 WAO MCP 服务。
- 只有 CLI 等待器做这项证明（同 0096）。
