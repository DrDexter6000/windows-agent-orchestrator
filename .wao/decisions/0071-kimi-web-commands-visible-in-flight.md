## 背景

kimi-web 的工具证据此前只在整轮结束、且带着 assistant 正文完成时才投影进转录。一条跑几分钟的命令在途期间，转录里只有 `streaming` / `serve_active` 两类事实——Lead 用 `run_activity` 看得到"还活着"，看不到"在跑什么"。

在途帧的形状（2026-10-13 真机探针，kimi 先 Read 再 Bash 跑 `sleep 45`，每 2 秒读一次服务端转录，只记形状）：

| 时刻 | Bash 帧 |
|---|---|
| 首见 | `state:"running"`，键为 `frameId` / `toolCallId` / `name` / `inputText`——没有 `input`，参数还在流式拼装 |
| 约 2 秒后 | `input` 就绪（`{command, timeout}`），`state` 仍是 `running` |
| 命令结束 | `state:"done"`，`output` 在场 |

Read 帧首见即 `done`。

## 决定

1. **工具证据在轮询期落盘。**（`src/backends/kimiWeb.js` 的 `projectKimiToolFrames`）每拍对归属本轮的 tool 帧按台账（键为 `frameId`）只发射还没落过的部分：
   - 命令 / 工具调用（command、tool_use）在**输入就绪**时落：要求 `input` 对象在场，shell 类另要求 `command` 已是字符串。首见那一拍没有 `input` 就等下一拍——否则 Bash 会因为还没有 `input.command` 被错分成 tool_use。
   - 结果（tool_result）在帧到终态（`done` / `error` / `failed`）时落。
   - 整轮带着正文完成时，把还没落过的全部补齐；同一帧不重复发射。
2. **写文件证据与失败路径不变。**
   - 写文件类的帧（Write / Edit / MultiEdit）在途不投影：`file_written` 仍只在这一轮带着正文完成时才落。没有正文的 completed 轮、失败 / 取消的轮不落写文件证据——既有保证（N1："不伪造完成"那组测试）原样成立。
   - 失败 / 取消 / 没有正文的 completed 轮，结束那一拍不补发任何证据；转录里只有在途时已经看到的命令与工具调用。
3. **MCP 硬上限**：Owner 明示确认 94532 字节（决定 0070 里 Lead 按 10% 口径落的数值）。记入 ADR-0032 修订节。

## 如实边界

- **失败的轮里会留下在途时看到的命令与工具调用**（此前失败的轮零证据）。留下多少取决于失败之前轮询到了哪一拍；从未在途观察过的轮（只在最后一拍看到）与此前完全相同。
- **写文件在途仍不可见**；一条正在执行的 Write 也不会出现，直到整轮完成。
- **参数拼装期间（首见到 `input` 就绪，探针里约 2 秒）命令还不可见。**
- 在途形状只在一次探针里实测过（一个 Read、一个 Bash）；其它工具的在途帧是否也是"先没有 `input`、后就绪"没有逐一验证——判据按"`input` 对象在场"写，不依赖具体工具。
