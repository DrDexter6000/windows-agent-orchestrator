## 背景

kimi-web 的工具证据此前只在整轮结束、且带着 assistant 正文完成时才投影进转录。一条跑几分钟的命令在途期间，转录里只有 `streaming` / `serve_active` 两类事实——Lead 用 `run_activity` 看得到"还活着"，看不到"在跑什么"。

在途帧的形状（2026-10-13 真机探针，kimi 先 Read 再 Bash 跑 `sleep 45`，每 2 秒读一次服务端转录，只记形状）：

| 时刻 | Bash 帧 |
|---|---|
| 首见 | `state:"running"`，键为 `frameId` / `toolCallId` / `name` / `inputText`——没有 `input`，参数还在流式拼装 |
| 约 2 秒后 | `input` 就绪（`{command, timeout}`），`state` 仍是 `running` |
| 命令结束 | `state:"done"`，`output` 在场 |

Read 帧首见即 `done`。

## 决定

1. **工具证据在轮询期落盘。**（`src/backends/kimiWeb.js` 的 `projectKimiToolFrames`）每拍对归属本轮的 tool 帧按台账只发射还没落过的部分：
   - 帧的身份是 `toolCallId` / `frameId`（两个都登记到同一个台账条目上，哪个先到、哪个后补都认得出是同一帧）。有身份的帧不重复发射；两个都没有的帧在途不投影——下标不是身份，帧被插入或重排时会张冠李戴——等整轮带着正文完成时才落。
   - 命令 / 工具调用（command、tool_use）在**输入对象就绪**时落：`input` 是非空对象，shell 类另要求 `command` 是非空字符串。首见那一拍没有 `input` 就等下一拍——否则 Bash 会因为还没有 `input.command` 被错分成 tool_use。这是形状判据，不是"参数已经完整、此后不变"的证明。
   - 结果（tool_result）在帧到终态（`done` / `error` / `failed`）时落。帧到终态时不看就绪判据：没有输入的终态帧照此前的规则投影。
   - 整轮带着正文完成时，把还没落过的全部补齐。每个事件的形状与此前的整轮投影相同；跨帧的先后不再等于帧序——在途已落的命令会排在更早的写文件帧之前。
2. **写文件证据与失败路径不变。**
   - 写文件类的帧（Write / Edit / MultiEdit）在途不投影：`file_written` 仍只在这一轮带着正文完成时才落。没有正文的 completed 轮、失败 / 取消的轮不落写文件证据——既有保证（N1："不伪造完成"那组测试）原样成立。
   - 失败 / 取消 / 没有正文的 completed 轮，结束那一拍不补发任何证据；转录里只有在途时已经落过的命令、工具调用及其结果。不变的是这两道门，不是"失败轮的转录与此前相同"——见下。
3. **MCP 硬上限**：Owner 明示确认 94532 字节（决定 0070 里 Lead 按 10% 口径落的数值）。记入 ADR-0032 修订节。

## 如实边界

- **失败的轮里会留下在途时落过的命令、工具调用及其结果**（此前失败的轮零证据）。留下多少取决于失败之前轮询到了哪一拍——失败轮的转录不是完整的执行清单；从未在途观察过的轮（只在最后一拍看到）与此前完全相同。下游随之变化：证据数与活动数增加；在途带 tool_use 的失败轮，诊断会从 `crash` / 未知翻成 `no_effect`（只跑过 Bash 的不翻——command 不计入那条判据）。在途事件里没有 `file_written`、没有退出码、没有正文，不会让失败轮通过审计或进入交付打包。
- **就绪之后输入若再被改写，落下的是当时看到的那一版**；结果落下之后 `output` 若再变也不更新。探针里没有见过这两种情况，也没有逐个工具验证过。
- **写文件在途仍不可见**；一条正在执行的 Write 也不会出现，直到整轮完成。
- **参数拼装期间（首见到 `input` 就绪，探针里约 2 秒）命令还不可见。**
- 在途形状只在一次探针里实测过（一个 Read、一个 Bash）；其它工具的在途帧是否也是"先没有 `input`、后就绪"没有逐一验证——判据按"`input` 是非空对象"写，不依赖具体工具。
