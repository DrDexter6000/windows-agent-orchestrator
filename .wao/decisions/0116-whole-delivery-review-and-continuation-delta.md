# 0116 交付审查可一次读完，续修轮可只看这一轮的改动；都走同一安全投影

- 日期：2026-11-07
- 状态：accepted
- 来源：2026-11-05 Lead 使用评审 consult_202611051157533033tik52 的 P1 与会审意见（kimi：“安全批量 CLI 审查”，最高频摩擦；sol：续修子运行打包的是谱系累计成果，审查要能只看本轮）；Owner 当日同意全部建议（C 批）。
- 关系：0112（窄缺陷交回原 worker 续修）；0114（续修接回原会话）。

## 背景

1. `run_delivery_review` 与 CLI `runs delivery review` 一次只给一个文件的一页（≤16KiB）。审查一份十几个文件的交付要几十次调用，实际里宿主 Lead 与会审席都改用 `git diff <base>..<delivery>`：绕过了逐字脱敏与控制字符清洗，也没有“仓库文本不可信”的标记。
2. 续修子运行从谱系原始 base 打包累计成果。审续修轮时，Lead 要看的是父交付之后这一轮改了什么，现在只能自己拿两个提交号跑 git。

## 决定

1. **一次读完**：CLI `runs delivery review <runId> --all [--out FILE]` 对每个变更文件、每一页调用同一个审查服务、经同一套投影，按文件拼成一份输出；开头写明全文是不可信的仓库文本；读不了的文件（binary、超限）照旧列出闭集原因。不加 MCP 工具（宿主调用时限与回包大小）。
2. **只看这一轮**：`--since-parent` 只用于续修子运行。父交付提交取自谱系事实，并在同一工作区里证明为父运行的交付提交；不接受调用方给的提交号。比较父交付提交与本运行交付提交，经同一脱敏、清洗与单文件上限。
3. 审查的正常路径是这两种之一或逐文件工具；本地只读 Git 仍只在 `binary`/`diff_too_large` 时使用。

## 已知边界

- 只有 CLI；只有 MCP 的宿主仍逐文件读。
- 单文件超过上限的仍是 `diff_too_large`，不因一次读完而放宽。
