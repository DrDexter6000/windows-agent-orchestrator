# 0085 隔离运行在终态的零丢失自动回收：只删干净的树，分支一律保留

- 日期：2026-10-16
- 状态：accepted（Owner 2026-10-16 同意"run 结束后自动回收运行树，不丢东西"；范围由 Lead 定）
- 来源：TD-146；决定 0082 第 4 条（"终态的零丢失自动回收……另议"）。
- 关系：在 0057 W1a、W1b 与 0058 lineage-close 之外，新增第四条树的自动释放路径。不改 0082，分支的删除仍只走批准的计划。
- 会审：方案会审 consult_20261016161118660fnic1u（sol、kimi）。实现批的会审记在提交说明里。

## 背景

- 现有三条自动回收路径之外的树，一直留着不删：
  - reject 和 failed 的交付；
  - 普通隔离运行；
  - 打包没有成功的交付运行。
- 存量靠 Owner 批准计划的 `wao worktree reclaim` 清，但新的积压一直在发生。
- 0082 第 4 条把"终态的零丢失自动回收"留作另议。

## 决定

1. **在哪里做。**Run 的终态收尾路径里新增一条释放臂，位置在停止确认之后、`run.cleanup_done` 之前（W1a 所在的位置）。它只处理本 run 的树。
2. **适用对象**，四条同时满足：
   - persistent 隔离树；
   - 派发时没有 sessionReuse 路由；
   - 不是 run_lineage 线系的成员；
   - 没有 `run.delivery_created`。打包成功的交付一律不碰，它们归 W1b、lineage-close 与 0082；打包失败而树全净的在适用对象内——能重新打包的形态树上一定有改动，会因内容在场而保留。
3. **删除条件**，全部成立才删：
   - 身份可证：树路径取自绑定事实，等于 `<run.started.cwd>/.wao-worktrees/<runId>`，与 git 登记、真实路径、common git dir 一致，路径上没有链接；
   - 没有别的尚未终态的运行以这棵树或它的子目录为工作目录（确有占用记 `tree_in_use`；存储读不出、判断不了记 `occupancy_unprovable`，同样保留）；
   - 终态已落盘，停止已确认；
   - 内容全净：包括被 ignore 的产物，以及清点不了的特殊状态；
   - HEAD 附着在 `wao/<runId>` 上，且等于它的 tip；
   - 树下没有嵌套运行树，树不被别的运行共享。

   任一条读不出或不成立，就保留，记下闭集原因。
4. **只删树。**
   - 删除不加 force。删不掉，或删后目录仍在，就保留，记 `still_present`。
   - 分支一律保留。提交都在分支上，删树不丢任何提交。
5. **不加 sweep。**hygiene、doctor、派发时都不顺带删除。收尾路径没处理到的树（进程崩溃、目录被占用），仍归 `wao worktree reclaim`。
6. **事件**沿用 0057/0062 的释放事件族，每个 run 记一条。

## 否决的方案

- **同时自动删零独有的分支：**超出 Owner 本次授权的范围（"回收运行树"），也越过 0082 第 3 条"分支只按批准的计划删"。要做，须 Owner 另行批准。
- **另加兜底 sweep：**会把删除带进没有在程属主的路径，活性只能靠磁盘证据推断。存量已有批准计划这个出口。
- **纳入已打包、又被 reject 的交付：**判定"已放弃"是 Lead 的语义判断（0057），不归自动机制。

## 已知局限

- **两套洁净标准并存。**W1a 释放只读树时不查脏，因为违规证据留在保留的分支上；本路径则查全部脏状态，含被 ignore 的产物。
- **分支照旧积累。**由 hygiene W4 计数，按 0082 的批准计划清退。
- **有一类树处理不到。**属主进程在终态之后、收尾之前崩溃，这棵树不会由本路径处理。
- **外部进程占用时可能删到一半。**比如有个 shell 停在树里：在 Windows 上，git 可能先删掉部分已跟踪的文件，再在被占用的目录上失败。这时记 `still_present`，提交都在分支上，残树归 `wao worktree reclaim`。
- **位置证不了的未终态运行会让所有自动回收停下。**以下情形，占用扫描整次判 `occupancy_unprovable`，对所有项目都一样：
  - 尚未终态、却没有可用 `run.started` 的运行，例如排队还没开跑、`run.started` 写坏、前台运行在 `run.started` 之前崩溃；
  - 打不开、读不出的文件。

  已终态的坏转录不挡。排队通常只有几秒。没开跑就死掉的运行，要先结算（`wao runs settle`）或归档。期间积下的树归 `wao worktree reclaim`。
- **扫描只看本 run 的运行存储。**保留目录（reliability、verify、smoke）和换了 runDir 的另一套存储不在扫描面内。
- **扫描之后派发进这棵树的运行看不到。**后果有界：不带 force 的删除遇到新的未跟踪文件会拒绝，最坏是那个新运行启动失败。
- **扫描是同步 I/O。**每结束一个适用的运行扫一次，代价随存储大小线性增长（2026-10-16 实测 1332 份约 1.8 秒）；daemon 里会阻塞事件循环这么久。
- **判定与删除之间有一个小窗口。**这期间若有外部操作者新建被 ignore 的文件，不带 force 的删除也会把它删掉。窗口在停止确认之后，只有外部操作者能碰到。
