# 0118 worker 交付验证跑定向测试，批次的全量只在最终候选上跑一次

- 日期：2026-11-08
- 状态：accepted
- 来源：workflow 地图第二轮建议 E1。Owner 当日答复（原话）："worker 的交付验证要不要改成只跑定向测试、全量只在最终候选上跑一次 —— 同意。理应如此。"
- 关系：修订 0077 第 3 条（"触及共享核心的仍用全量"）；0077 第 1 条（每批只在最终候选上跑一次全量）、0110（只改文档的批次不跑全量）不变。

## 背景

1. 0077 第 3 条让触及共享核心的 worker 交付以 `npm test` 作验证命令。第 83 批四份交付各跑一次、一次重验、最终候选一次，共六次全量，每次 18–41 分钟，一次撞到 60 分钟上限；同机验证闸让它们排队。
2. 交付验证时 main 上还没有同批的其它交付，集成之后的回归只有最终候选那次全量看得见。交付侧的全量大多在重复最终候选的工作；首轮偶发红（TD-194）还会把一份正确的交付判成验证失败，Lead 要重验或走采纳协议。

## 决定

1. 触及共享核心的 worker 交付，`verificationCommands` 逐个列出测试文件：被改模块的直接测试、读被改文件的测试（按文件名搜）与横切守卫组，不用跨文件通配；具体加哪些守卫以 `docs/testing.md` 的交付表为准。
2. 公共夹具与测试运行器（`test/fixtures/**`、`test/_*.mjs`、`test/reporter.mjs`、`scripts/canonical-test.mjs`、`scripts/test-one.mjs`）的交付仍用 `npm test`，并声明 `verificationTimeoutMs ≥ 1200000`：运行器的改动影响每一次全量与定向运行，被改的定向运行器也不能自己验证自己；公共夹具读者多，按文件名搜容易漏。
3. 批次的全量照 0077 第 1 条只在最终候选上跑一次，第 2 条那类交付的验证另计。最终候选的全量红了，照批次规则处理：窄缺陷交回原 worker 续修或由 Lead 修，修完在新的最终候选上再跑一次。

## 被否方案

- 交付侧跑全量、最终候选不跑：集成之后的回归看不见。
- 交付侧连定向测试也不跑：交付自身的缺陷要拖到最终候选才发现，返工更远。

## 已知边界

- 定向测试漏掉的跨模块回归，要到最终候选的全量才暴露；那时可能已有几份交付集成在一起，定位更费事。
- 列哪些测试靠 Lead 判断；按文件名搜可能漏掉间接的读者。
