# 0121 zcode 停滞门用一个作业对象认运行的进程（Windows 临时方案）

- 日期：2026-11-09
- 状态：accepted
- 来源：台账 TD-346；第 94 批。方案经 kimi、sol 两席方案审查（都判 REVISE，改法已采纳）；Owner 2026-11-09 原则批准，并要求注明：**这是针对 Windows 平台的临时解决方案，将来做其他系统平台的适配开发时要注意这一点**。
- 关系：决定 0013 选择不实现自定义 Job Object，针对的是进程隔离与击杀（父死全杀）；本决定为 zcode 停滞门放开一个 WAO 只用来观测、从不主动击杀的作业（它对进程生死的附带影响见决定第 5 条，与 0013 同向），0013 的其余内容不变。

## 背景

实测（2026-11-09）：

1. zcode 停滞门在模型不出流时，以 app-server 为根，按 `Win32_Process.ParentProcessId` 走树取后代的 CPU、I/O 与进程生灭。
2. zcode 经 Git Bash 跑命令。直接跑原生程序时父子链完整；跑 `#!/usr/bin/env bash` 脚本（`npm`、`npx` 都是）时，bash fork 的子进程 exec `env`、`env` 再 exec `bash` 后几毫秒内退出，新 bash 的父进程号指向已退出的进程，其下整条链挂不上树。原样复现第 90 批的 `npm run test:one -- test/delivery/runDeliveryRepackage.test.js`：约 4 分钟里每个 30 秒窗都判"无体征"，测试子进程其实一直在用约 200 ms/s CPU。worker 跑较长的 npm 命令时会被误收。
3. MSYS 自己的 `ps` 表补不上这一跳（断开后的进程 PPID 为 1，占位进程与它没有关联记录）。
4. 进程加入作业是在创建时继承的，与父进程是否还在无关：断链后的进程都在作业里，作业的累计 CPU、I/O 与进程总数（含只活几毫秒的进程）都读得到；给已在 libuv 作业里的 app-server 再加一个嵌套作业可行。
5. MSYS 建进程前查当前作业：作业允许脱离（`BREAKAWAY_OK`）时它会主动脱离，被找的进程又逃出去。libuv 起 detached 子进程不请求脱离。
6. 作业名只在有进程持有句柄时存在：建作业的进程退出、没人持有句柄时按名打开报 err=2；把句柄复制进 app-server 后，建作业的进程可以退出，app-server 退出时名字随之消失。

## 决定

1. 只在 Windows、只对 zcode 后端：app-server 起来后，由一次性 PowerShell 建命名作业（**不设任何限制标志**：不 kill-on-close、不 `BREAKAWAY_OK`、不 `SILENT_BREAKAWAY_OK`），把 app-server 加进去，再把作业句柄复制进 app-server，然后退出。不常驻任何进程。
2. 就绪屏障：作业挂好（或确认挂不上）之后才发会话的 resume/create 与任务；挂不上不阻止派发，退回只按进程树判断，并在转录里落一条系统消息说明原因。
3. 停滞门的进程证词 = 进程树有活动 **或** 作业有活动。作业读数在同一次快照里取，窗内增量减去 app-server 自身的 CPU 与 I/O（控制面每拍向它要快照，它自身的读数恒涨）；进程总数增加或在跑进程数变化也算活动。计数回退或读不到时，这一窗的作业证词记为不可用，不当作"无活动"。
4. WAO 只拿作业来观测：不调用 `TerminateJobObject`，不改收尾与 `wao stop` 的击杀；其他后端不接。
5. 接受挂作业带来的一个生死变化（会审实测）：runner 不带 detached 起 app-server，app-server 在 runner 的 libuv 作业里（关作业即杀、允许静默脱离）。以前 app-server 之后起的子孙静默脱离那个作业，runner 退出后还活着；挂上不许脱离的内层作业后，它们不再脱离任何一层，runner 退出时随之结束。正常收尾时 zcode 本来就用 `taskkill /T` 结束 app-server 整棵树，变化只落在 `taskkill /T` 走不到的 MSYS 断链孤儿和 runner 异常退出这两种情形：以前漏成孤儿，现在随 runner 结束，与决定 0013 的"进程死即会话死"同向。app-server 的插件宿主与 MCP 服务都是每个 app-server 各一份，不跨运行共用。

## 被否方案

- **按 MSYS 进程表补链**：表里也是断的（实测 3）。
- **短命进程建命名作业、每次取样再按名打开**：名字随句柄消失（实测 6）。
- **常驻 PowerShell 助手持有作业句柄**：可行，但多一个要管存活、卡死、新鲜度和回收的进程；句柄复制进 app-server 省掉这些。
- **把"父进程已退出、创建晚于 app-server"的孤儿都算进来**：多个 worker 并行时互相记账，卡住的运行会被别人的测试撑着不收口。
- **在 PATH 前面放 `#!/bin/sh` 的 npm/npx 外壳**：只治 npm/npx，还改了 worker 的环境。
- **工具调用在途时豁免停滞门**：停滞门本来就要抓卡住的工具调用。

## 已知局限

- **只在 Windows 上有效，是临时方案。** 其他平台的进程树、会话与作业机制不同，适配其他平台时要另行设计，不能沿用本决定的做法。
- 加入作业之前 app-server 已经起的子进程不在作业里（不追溯），仍只靠走树。
- 明确请求脱离作业的程序会建进程失败（作业不允许脱离）；MSYS 与 libuv 都先查再请求，不受影响。
- 每次派发多一次挂作业的 PowerShell（实测约 0.7–1.1 秒）；停滞门每次取样多一次 `Add-Type` 编译（约 0.2–0.3 秒）。挂作业期间收不到中止信号（spawn 阶段本来就拿不到），最多多等 15 秒。
- 作业读数一时读不到按瞬时失败处理，连续 3 次才退回只看进程树与工作树。
- 经 WMI 等不继承作业的途径起的进程看不到。
