# 0079 kimi worker serve 空闲退出：跟着 serve 走的看护进程

- 日期：2026-10-14
- 状态：accepted（做法由 Lead 在 Owner 裁定下确定）
- 来源：Owner 2026-10-13 对决定 0075 收尾报告的回复（原话）——"3、kimi serve 的寿命：可改成空闲退出；"。0075 的收尾报告把 serve 的寿命单列出来请 Owner 定。
- 关系：决定 0075（按需拉起；本决定取代它第 7 条里的"不做空闲自动关闭"）；决定 0056（serve 维护不挂 daemon）；决定 0074（serve 环境剔除密钥类变量）。
- 合入授权：Owner 2026-10-12——"只要是你联合会审过的，我都许可 commit & push"。

## 背景

- kimi web 没有空闲超时选项（`kimi web --help`，kimi 2.1.1）。
- WAO 没有常驻进程：派发由 runner 进程执行，运行结束它就退出。
- 0075 起，声明了 `serveWorkspaceDir` 的车道在派发时按需拉起 serve。拉起后它一直运行，直到关机、手动 shutdown 或 recycle。

## 决定

1. **WAO 自己拉起的 serve 带一个看护进程**，包括按需拉起与 `serve recycle` 重启的。看护进程的形状：
   - 用 `process.execPath` 跑 `src/backends/kimiServeIdleWatch.js`，以 detached、隐藏窗口、不接 stdio 的方式启动；
   - 环境按 serve 的剔除规则处理，不带密钥类变量、`WAO_*`、`CLAUDE*`、`ANTHROPIC*`；
   - 主目录经命令行参数传入，token 每拍从 `<主目录>/server.token` 读，不经环境。
2. **空闲的判定**：默认与归档两面会话列表里没有 `busy` / `main_turn_active` 的会话，且会话 id 集合与上一拍相同。token 或列表读不到的那一拍不算空闲，计时重新开始。60 秒一拍，连续空闲满 30 分钟后：
   - 抢 0075 的那把启动锁。抢不到就跳过这一拍；陈旧的锁只在确认持锁进程已不在时接管，持锁者活着或认不出来（锁里没有 pid、内容读不出来）都不碰；
   - 抢到后再读一次两面列表，仍然空闲；
   - 关停按端口发出，所以之前再核对一次：被看护的 pid 还是活着的 kimi 进程，且这个端口的实例记录属于它。不是就退出（`serve_gone` / `serve_replaced`），不关端口上别的 serve；
   - 请 serve 优雅关停（`POST /api/v1/shutdown`），最多等 15 秒确认端口不再监听，然后放锁退出。
3. **只优雅关停，不杀进程。** 以下情形看护都直接退出，什么也不做：关停请求失败；token 连续 3 拍读不到；会话列表连续 5 拍读不到；serve 的 pid 已不是同一个 kimi 进程。
4. **serve 退出之后：** 下一次派发发现端口没有监听，按 0075 重新拉起，并带上新的看护。
5. **不带看护的 serve：** 手动脚本 `scripts/kimi-serve.ps1` 拉起的 serve 不带看护，一直运行到有人关掉。
6. **Lead 看得到：** 按需拉起的 system 说明写上看护 pid 与阈值；看护起不来时如实写"serve 会一直运行到手动关掉"。`serve recycle` 的 JSON 结果带 `idleWatch`。
7. **启动看护的函数由调用方注入：** kimi-web backend 交给按需拉起，serve 命令交给 recycle。拉起原语不 import 看护模块，两个模块之间没有循环依赖；库层直接调用时不注入就不起看护，单测因此不会真起进程。recycle 只给本次重启、且在目标端口上登记了实例的那个子进程配看护，否则结果写 `not_own_child`。

## 否决的备选

- **每个 kimi 运行结束时立即关停 serve。** 每次派发都要付 2–4 秒冷启动；并发运行和续接会话会被正在关停的 serve 切断。
- **随 Lead 宿主退出时关停。** serve 是各宿主共用的，一个宿主退出时别的宿主可能还有在途运行；宿主退出也没有可靠的钩子。
- **常驻守护进程统一管理。** Owner 不接受常驻进程与开机自启（决定 0075），决定 0056 也定了 serve 维护不挂 daemon。

## 已知边界

- **复核与关停之间的窗口：** 复核与关停请求之间仍有极短的窗口。恰好此刻到来、首探成功的派发，建会话时可能撞上正在退出的 serve，以传输错误失败；下一次派发会重新拉起。
- **看护的异步启动错误会被吞掉：** 极少数情况下，说明里写了看护 pid，实际却没起来，serve 会一直运行到手动关掉。
- **看护没有总运行上界：** serve 一直有活动时看护一直在，每 60 秒发两次会话列表请求，并做一次进程核验。
- **没有看护的 serve：** 本决定之前拉起的 serve 和手动脚本拉起的 serve，都没有看护。

## 验证

单测全部注入（spawn / fetch / 时钟 / 锁 / 实例表），零真进程。真机验证（recycle 带起看护、空闲后优雅关停、下一次派发重新拉起）的结果写在合入提交的说明里。
