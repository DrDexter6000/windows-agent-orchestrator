# 0123 kimi-code 与 deepseek-harness 两个 worker 后端退役，巡检留观察表

- 日期：2026-11-10
- 状态：accepted
- 来源：
  - 2026-11-10 harness 巡检后，Lead 在 TD-117 建议两个后端都退役。Owner 问："有没有可能某一天官方加强了cli通道，最后发现强于dsh的acp和kimi-web —— 如果我们删除了，会不会无法及时发现这种升级/加强（因为主动忽略了）？"
  - Lead 给了三个方案：A 两个都退役，巡检加观察表；B 只退役 deepseek-harness；C 都不删，只加观察表。Owner 答"同意方案A"。
  - 第 101 批。
- 关系：修订决定 0074 第 4 条（"代码与测试保留"）；做法同决定 0105；TD-117 由本决定关闭。

## 背景

- kimi-code 驱动 kimi 的无头命令行（`kimi -p … --output-format stream-json`）。它的输出不报 token 用量，工具失败只能按输出关键词判断。kimi 车道从 2026-10-01（决定 0036）起走同一程序的 `kimi web`（kimi-web 后端）。
- deepseek-harness 驱动一个单独的 JSON-RPC 入口程序 `dsh-jsonrpc-agent`。本机没装，候选 npm 包查询 E404，也不支持会话复用。dsh 官方给外部工具的对接方式是 ACP，WAO 用的是 deepseek-acp。
- 两个后端从 2026-10-13 起不配车道（决定 0074），之后没跑过一次真实任务，只靠单元测试保持绿灯。这期间 WAO 新加的停滞门生命体征、作业对象等机制都没在它们身上验证过。
- 巡检的对象 = KNOWN_BACKENDS 闭集，原语表一个后端一行。直接删后端，巡检就不再看这两条通道，这正是 Owner 担心的。

## 决定

1. 从工作树删除两个后端、kimi 的 stream-json 解析器、它们专属的测试与假运行时、kimi-code 的会话复用证据，以及各处只为它们存在的分支（构造、注册表校验、环境变量白名单、凭据就绪、CLI 映射、模型族、引导、doctor、可靠性脚本）。KNOWN_BACKENDS 7→5。
2. 两个 annotated tag `archive/kimi-code-backend`、`archive/deepseek-harness-backend` 指向退役前最后一个含它们的 main 提交。取回用 `git checkout <tag> -- <路径>`，测试一并取回，按当时的机制重新适配并认证后才能派发。
3. 只把它们当通用替身的测试（进程型后端的会话复用、占位会话拒绝、能力警告等）迁到在用后端，共享代码的覆盖不减。
4. 保留：kimi 作为 MCP 宿主（宿主 id `kimi-code`）、kimi-web 车道的 `~/.kimi-code` 主目录、deepseek-acp。决定、事故、调研与归档里的历史照原样保留；转录里写着这两个后端名的旧运行照常可读。
5. `docs/certification-runbook.md` 的 harness 版本巡检加一张"未接线通道观察表"。每次巡检读在用通道的更新说明时，顺带对照表里的接回条件；条件出现就报 Owner，提议走"接线"分叉。这张表不进闭集，不设原语行和守卫。

## 被否方案

- 留作休眠代码（方案 C）：留着代码不等于能发现上游变化。真要启用，照样得重新适配和认证，而闭集、能力表、生成层和测试一直要带着它们。
- 直接删、不留观察表：巡检会从此不看这两条通道。
- 只退役 deepseek-harness（方案 B）：kimi 命令行确实比 dsh 的 JSON-RPC 入口更可能接回。但接回时同样要重新适配，留着代码省不了这一步。

## 已知局限

- 取回不是单文件即用：要连测试一起恢复，再按当时的机制改过、重新认证。
- 观察表靠巡检时人读更新说明，没有守卫兜底。漏读的风险和原语表的渠道列一样。
