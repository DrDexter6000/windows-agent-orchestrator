## 背景与实测

重启机器后 kimi 的 worker serve 不在，kimi 车道报连接被拒。决定 0074 的收尾把这件事写成"需要人手动拉起"。这没有技术障碍，也不需要额外授权——只是没有做成自动的。

实测（2026-10-13，kimi 2.1.1，Node 22，本机）：

**启动方式**

| 启动方式 | serve 在拉起它的进程退出后 | worker 跑命令时的可见窗口 |
| --- | --- | --- |
| Node `spawn`，`detached: true, stdio: "ignore"`（recycle 一直用的形状） | 继续运行 | 0 |
| Node `spawn`，只给 `windowsHide: true`、不给 `detached` | 消失（之后十几秒里六次探测全部连接被拒，进程不在） | 没测到这一步 |
| PowerShell 脚本 `scripts/kimi-serve.ps1`（隐藏窗口） | 继续运行 | 0 |

"可见窗口"的量法：让 kimi worker 跑一条 14 秒的 `ping`，同时每 0.4 秒枚举 serve 的全部后代进程（实见 `bash.exe`、`conhost.exe`、`PING.EXE`），查有没有哪个持有可见的顶层窗口。只覆盖了 shell 命令这一种工具。

冷启动到会话面应答：2–4 秒（四次有读数的拉起）。

**端口被占时的第二个 serve 不会退出**（用一个临时的空主目录和备用端口量的，没有碰在用的 serve）：同一主目录、同一个 `--port N` 再起一个 `kimi web`，它改绑 N+1、照常登记实例，20 秒后仍在运行，直到被关。也就是说，重复拉起不会自己消失，会留下一个没人用的 serve。这决定了下面锁和事后核对的做法。

**首次启动会生成 `server.token`**（同一次测量）：空主目录里第一次 `kimi web` 起来后，`server.token` 就在了，不需要先登录。

## 决定

1. **kimi-web 车道可声明 `serveWorkspaceDir`**（绝对路径，worker serve 的工作目录）。声明后，每次派发（含续接轮）在建会话之前先探一次 serve：连接被拒 → 进入拉起流程；首探是别的任何结果（HTTP 应答、超时、其它传输错误）→ 不动，照常由请求路径报错。没声明的车道行为不变，连探测都不发。只在回环地址上拉。
2. **拉起流程去重，并事后核对**。
   - 启动锁：系统临时目录下按端口的一个文件。拿到锁的派发去拉，其余等待应答。放锁只删自己的；陈旧（120 秒）可接手；内容读不出来的锁按文件修改时间算陈旧；锁文件写不了就不拉，报错点名位置。
   - 有活着的 serve 进程就不再拉：这个端口的实例记录心跳新鲜且那个 pid 确是活着的 kimi 进程（serve 活着但没在监听——正在退出或挂住了）；或上一次拉起的 kimi 进程还活着却一直没应答（它的 pid 记在留下的锁里）。这两种情形只等，等不到就报错并点名 pid。**不杀进程。**
   - 事后核对：拉起者查自己那个子进程的实例记录。不在目标端口上 = 目标端口在这期间被别人占了、自己多拉了一个 → 用同一主目录的 token 请它优雅退出，并在说明里写明。只动本次派发自己刚拉起的那一个。
   - `serve recycle` 在"关旧的、起新的"这段窗口里占同一把锁，这期间到来的派发只等。
3. **等待**：等到会话面返回成功为止，上界 45 秒（自首探之后起算；单次探测另有 4 秒超时）。端口有 HTTP 应答但不是成功（例如不认这条车道的 token）连续 5 拍 → 不再等，交回请求路径去报真实原因。探测超时与传输错误不算应答，继续等。
4. **启动原语只有一份**：exe 候选链、工作目录的形状门与放置门（不在 `.wao-worktrees` 下、不在 kimi 主目录内、不在任何 git 工作树内）、环境组装、detached spawn 与 'error' 仲裁，从 recycle 的重启段迁到 `src/backends/kimiServeStart.js`，recycle 与按需拉起共用。
5. **serve 的环境不带 WAO 自己的变量**（`WAO_*`，不分大小写），`WAO_IN_WORKER=1` 在剔除之后注入。起因是会审指出的一条路径：嵌套派发的命令级豁免（`WAO_ALLOW_NESTED_DISPATCH`，决定 0047）若在拉起者的环境里，会跟进长命 serve，成为此后所有 worker 的常驻豁免——守卫先看豁免、后看 worker 标记。这条规则对 recycle 同样生效（共用原语），手动脚本也对齐了。密钥类变量照旧剔除（决定 0074）。
6. **Lead 看得到**：本次派发拉起过 serve、等过别人拉起、或把多拉的那个请走了，run 事件流的第一条是 system 说明（pid、端口、等了几秒）。拉起之后的步骤（建会话、提交）失败时，说明附在错误消息末尾。拉不起来，派发在建会话之前失败；原因取自闭集，不含 token、serveUrl 和上游正文。
7. **不做**：开机自启、常驻守护进程、harness 启动时预拉、空闲自动关闭、自动 recycle / sweep、杀进程。

## 为什么是"派发时"，不是"harness 启动时"

Owner 的建议是跟着 Lead 的 harness 启动。两种做法都满足他那两句话里的硬要求：不用人动手，没有开机自启。取"派发时"的理由：

- 不是所有派发都经过 MCP server 的启动：命令行派发（`wao run`、会审）没有这一步。
- 没用到 kimi 的会话不会平白起一个 serve。
- serve 中途没了（被关、崩溃），下一次派发自己补上。

差别：

- 时机：serve 不在时，第一条 kimi 派发多等几秒；harness 启动时预拉则把这几秒放在开宿主的时候。
- 寿命：serve 不随某个 harness 退出而关。它是各 Lead 宿主共用的，一个宿主关掉时别的宿主可能有在途的 kimi 运行。**这一点是 Lead 的取舍，Owner 没有表态**——"讨厌开机自启"推不出他接受或反对"宿主关了 serve 还留着"。收尾报告里单独请他定；要改成随宿主退出或空闲自动退出，与本决定不冲突。

## 与决定 0056 的关系

0056 定的是 serve 维护"不挂 daemon、无自动触发"，理由两条：worker serve 全机共享、归属含糊；自动重启时环境组装出错，会让 0047 的 env 臂静默失效。

本决定只放开一件事：**端口上没有监听、也没有活着的 serve 进程时，把 serve 拉起来**。对那两条理由：

- 归属：不关、不重启、不清扫任何在跑的实例。"端口没有监听"不等于"没有活着的进程"——所以另有两道存活检查和与 recycle 共用的锁（决定第 2 条）。
- 环境：由唯一的一份原语组装，`WAO_IN_WORKER=1` 恒注入，WAO 自己的变量（含豁免）不继承，都有测试钉住。会审前的版本没有做到后一点。

一个如实的性质变化：声明了 `serveWorkspaceDir` 的车道，手动 shutdown 掉的 serve 会在下一次派发时被拉回来。这是声明该字段的含义。

## 本机配置（不在仓库里）

`config/agents.json` 的 kimi 车道加 `serveWorkspaceDir = D:\projects\.kimi-serve-worker-ws`。合入之后执行。

## 行为变化与如实边界

- **声明了 `serveWorkspaceDir` 的车道，每次派发多一次回环请求**（探测）。
- **serve 仍然继承拉起者的其余环境**。去掉的是密钥类变量和 `WAO_*`；Lead 宿主的会话变量会跟进 serve 和此后所有 worker 的工具进程（实测从本会话拉起的 serve，worker 里看得到 29 个 `CLAUDE*` 变量名）。手动脚本另外去掉了 `CLAUDE*` / `ANTHROPIC*`，按需拉起没有。没有发现由此造成的功能问题，但 serve 的环境因此取决于"谁先派"。
- **锁不是原子的互斥**。"读到陈旧"与"删掉重建"之间别人恰好建了新锁，会多拉一个；多拉的那个由拉起者的事后核对请走。事后核对依赖 kimi 写实例记录：子进程没登记就挂住的话，核对看不到它。
- **起了进程却 45 秒没应答**：派发失败，那个进程不杀、留着，锁也留着并记着它的 pid；它活着期间后来的派发不再拉，报错点名它。它退出且锁过了 120 秒，下一次派发才重新拉。
- **崩溃或断电后一分钟内**的派发可能被"serve 活着但没在监听"挡一次——仅当旧实例记录心跳还新鲜、且那个 pid 恰好被另一个 kimi 进程复用时。
- **端口被别的主目录的 serve 占着**：首探得到的是鉴权失败，算有应答，不拉；派发照旧以鉴权错误失败。
- **serve 的寿命**：拉起后一直运行到关机，或有人手动 shutdown / recycle。Lead 宿主退出后 serve 是否存活没有实测（它与 runner 用同一种 detached 方式启动，设计上不依赖宿主）；即便被带走，下一次派发会再拉。
- **窗口**：这样拉起的 serve 没有控制台，worker 的工具进程由 kimi 自己创建。实测一条 shell 命令没有可见窗口，没有覆盖别的工具类型。
- **首次使用的私有主目录**（还没有 `server.token`）不会被自动拉起：token 文件缺失时派发在更早处就拒绝了（决定 0074）。第一次要用脚本拉起（脚本只要求主目录存在；启动后 token 文件自己生成）。
- **system 说明算一条消息**：`run_wait` 的进展计数和"首条消息即 running"的状态迁移会把它算进去——它不代表模型已有产出。取终稿、scorecard、交付、`run_await_result` 只认 assistant 消息，不受影响。
- **尚未重启的 Lead 宿主**：派发由新起的 runner 进程执行，runner 加载的是磁盘上的代码，所以旧宿主的派发同样会走到按需拉起；旧代码的注册表校验不拒绝未知字段。这一条在合入前没法实测（宿主跑的是主检出）。
- **`serve recycle` 仍然要显式给 `--workspace-dir`**，没有改成缺省取车道的 `serveWorkspaceDir`。recycle 自己拉起的子进程没有做"落在哪个端口"的事后核对（它占着锁，窗口内没有别的拉起者；此前就没有）。
