# 0076 文档体系：一项事实一个归宿；台账与决定索引守形状

- 日期：2026-10-13
- 状态：accepted（Owner 2026-10-13 指令；方案经 sol、kimi 两席会审后由 Lead 定稿）
- 来源：Owner——台账"应当必须立即解决"；"违反 SSOT 原则、管理体系官僚化、构架臃肿不优雅"是最反感的；"有什么机制可以保证未来的开发 lead agent 尽可能不再犯这个错？"
- 范围：本决定分两步落地。这一步是规则、台账、决定索引；活文档的清理与 `docs/usage.md` 的拆分是下一步，登记在台账 TD-34、TD-177。

## 背景

文档体系只会长、不会缩，而且是制度让它长的：

- 台账 `docs/tech-debt.md` 394,909 字节、267 条，最长一行 36,549 字节。2026-10-02 归档过一次，同时写下"新行不超过 2KB、超 80KB 再归档"，没有测试守着；归档后 245,834 字节，11 天后回到 394,909。
- 决定索引的头注写着"一行一条，不放正文"，同样无守卫，最长一行 2,684 字节。
- 文档守卫 `test/isolation-infra/docs-consistency.test.js` 265,648 字节、198 条测试，其中约一百条以里程碑号、TD 号或决定号命名，许多是"某文档必须出现某句话"。被钉住的句子删不掉、挪不动，`docs/usage.md` 因此一直拆不了。
- 功能提交通常要改 4–9 个文档文件：决定、索引、台账、usage，再加 runbook、排障手册、onboarding、示例配置注释。各处是换了说法的复述，逐字重复很少，查重查不出来。
- 主文档有字节上限，architecture 余 0 字节、usage 余 8 字节。上限顶到头之后的实际做法是删修饰语；决定 0075 有一条会审必改因为上限被放弃。

"一处定义，处处指针"早就写在 `docs/ssot.md` 里。它没守住，是因为同一批规则文本还要求着相反的事：里程碑收尾要在台账和审计两处同步、roadmap 要附测试数、契约一变就要追加一条决定、新建文档只许是事故复盘或决定、文档测试红了"修文档不修测试"。`AGENTS.md` 那句"默认更新既有权威"则被执行成了往既有的行里追加。

## 决定

1. **一项事实只有一个可编辑的归宿，其余地方只链接。** 一次改动写什么，规则在 `AGENTS.md` §Documentation：代码与测试；受影响读者的那一处参考文档；只有在备选之间做了取舍时才写决定档；债务开立或了结时台账一行。批次经过（改了什么、怎么验证、谁审的、运行与会审编号）写进提交说明。
2. **台账只放还没了结的事项，一条一行。** 五列（编号、问题、状态、何时处理、指针），状态只有开放、等待裁定、设计性约束，一行不超过 700 字节，更新是改写。了结的行移到 `docs/archive/tech-debt-closed.md`。重建前的整份旧台账原样移到 `docs/archive/tech-debt-2026-10-13.md`，只供查历史，不作现状的依据。每个编号只在台账、已了结清单、已偿还归档三者之一有定义行。
3. **决定索引一行只放编号和标题；新决定档不超过 8KB**，写背景、决定、否决的备选、已知边界。
4. **只在历史上被写成流水的三处留形状守卫**：台账的行、索引的行、新决定档的体量。文档测试今后只做四类：与代码一致、废除的说法不回来、形状、读者离不开的少数操作说明（在它的唯一权威处检查）。被保护的文字退役时，测试一起退役。
5. **与上面冲突的旧条款同批退役**：里程碑纪律里"台账与审计两处同步""roadmap 附测试数"；`ssot.md` 里"契约变了要追加一条决策""新建文档只有两种场景"；`AGENTS.md` 里"默认更新既有权威"；守卫文件头注"修文档不修测试"；钉旧台账分节结构与叙事文字的八条测试。

## 否决的备选

- **给活文档里的日期、TD 号、里程碑标签设只减不增的计数上限**（Lead 初稿）。日期可能是现行证据（认证基线日），TD 号可能指向现行限制，里程碑是 roadmap 的业务对象；换个写法就能绕过。计数只适合清理时观察。
- **给守卫文件设字节上限，或对全仓库的文档断言计数。** 控制错了对象：拦不住把钉点写到别的测试文件，却会拦住合理的关系型检查。
- **把"最多写三处"当硬限制。** 三处各自仍可以无限长。约束应当是"一项事实一个归宿"。
- **把"未实测"做成台账状态。** 验证程度与债务状态是两条轴；这个状态没有推动力，会变成停车场。各决定里"未实测"的说明留在决定里，只有明确要做的事才进台账。
- **冻结快照加头注。** 与"逐字节不变"矛盾。旧文件原样移动，说明写在归档目录的 README。
- **由脚本从决定档标题生成索引。** 仓库已有决定写入器，本来就只写编号加标题；索引变长是手工追加的摘要造成的，守形状即可。
- **再写一条"先看结构再打补丁"的原则。** 决定 0034 已有，重复一遍正是要治的问题。
- **每个批次固定上报文档指标。** 需要时从 git 抽查完整批次即可，不建例行填表。

## 已知边界

- 旧条目的去向是按旧表文字判定的，没有逐条对代码核实。判为已了结的 86 条连同依据列在已了结清单里。判错的后果是一个仍然存在的问题不在台账上；原文仍在冻结快照里。
- "参考文档只写现状""测试随被保护的文字退役"没有机器守卫，靠评审。
- 这一步没有动活文档的正文、主文档的字节上限和历史收尾类测试：usage 仍是单个大文件，architecture 仍余 0 字节。
- `docs/ssot.md` §0.1 的必读表没有改；seat-certify 的全文必读集合不变，其中的台账由 395KB 变为约 22KB。
