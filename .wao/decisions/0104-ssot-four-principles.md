# 0104 SSOT 四原则以 ssot §2 为家；AGENTS.md 只留指针，并写入"精简优先"

- 日期：2026-10-31
- 状态：accepted
- 来源：Owner 2026-10-31，原话如下。
  - "1、每一个事实称述/规定要求，原则上只由一份文件/文档来来申明；2、除非技术必要，项目的文件/文档中不出现重复的内容；3、如有技术必要，项目的文件/文档应用指针相互引用（而非重复）；4、原则上讲，项目的文件/文档都必须在workflow的某一环节被引用，不应该成为孤儿文件/文档（如果有孤儿文档/文件，则应该考虑清除掉，不要无限堆积无用artifacts、造成系统臃肿）"
  - "历史决策文件、log文件等作为留档备查、如果已经进archive、而且archive本身有结构化的归档构架、有大致地图导向 —— 那么可以保留"
  - "简练就是美"、"灵活就是美"、"官僚（除非工程和技术必要）就是丑"
- 会审：workflow 地图与整体方案经四席会审（consult_20261031182256481khrt6t）。

## 背景

`docs/ssot.md` §2 原是"三条铁律"；`AGENTS.md` 的 Documentation 一节另有六条规则，其中几条与 ssot、台账表头重复。一条规则散在几处，改的时候就要改几处，漏一处就漂移。

## 决定

1. `docs/ssot.md` §2 是 SSOT 原则唯一的家：Owner 的四条原则，加配套三条——"类别不可混放""过程文档只追加""活文档只写现状"（四条原则不覆盖前两条，所以保留）。旧铁律 1 对投影的要求照旧：技术上必要的第二份陈述限于 §2 表里的三类，每份在原处写明投影自哪里，含数值、闭集或计数的要有关系型守卫。改一条规则的做法写在 §2 末尾。
2. `AGENTS.md` 的六条文档规则逐条搬进 ssot §1.2–§4 与台账表头，`AGENTS.md` 只留一句指针。
3. Owner 的"精简优先"写进 `AGENTS.md` 开头：每个开发 agent 都读它，它管的是架构、文案与流程，不只是文档。

## 被否方案

- 用四条原则整体替换三条铁律：会丢掉"类别不可混放"与"过程文档只追加"。
- `AGENTS.md` 保留六条规则作摘要：与 ssot、台账表头重复，正是原则 2 要消除的。
- 精简原则写进 ssot：它管的不只是文档。

## 已知局限

- 原则 4 还没有机械检查；可达性检查随 `npm run map` 落地，先只出报告。
- 事故与 changelog 两个档案馆还没有门户。
- 仍有现行规则住在决定档里（如 0032、0045、0038），另批按类别搬到现行的家，旧决定只追加修订指针。
