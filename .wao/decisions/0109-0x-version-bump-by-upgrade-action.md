# 0109 0.x 阶段的版本号：要动手的升 MINOR，向后兼容的升 PATCH

- 日期：2026-11-03
- 状态：accepted
- 来源：Owner 2026-11-03 问："你看我们最近一个月以来，每一次升级都是一个minor小版本的升级……是不是我们的version里的那个规则有些问题可以调整一下"；看过 Lead 的审视与提案后答"按此方案推进"。
- 关系：部分取代 0038 第 1 条的版本号映射（只管 1.0.0 之前）与 0038 后果节的快照条款；0038 原文保留不改。0038 第 4 条（1.0.0 门槛 = TD-194 关闭）与第 5 条（发版门槛）不变。

## 背景

2026-10-01 到 11-02 发了 8 个版本，7 个 MINOR，PATCH 只有 v0.3.1。0038 第 1 条让"新增能力升 MINOR"，而几乎每个周期都会加命令、参数或字段；同一条又让 0.x 的破坏性变更留在 MINOR。于是 v0.6.0（删了命令）、v0.8.0（旧注册表条目失效）要用户动手，v0.5.0、v0.7.0 只是新增，版本号上看不出区别。

升级 WAO 的人想从版本号知道的是"升级后要不要动手"。npm 的 `^0.8.0` 与 Cargo 都把 0.x 的 MINOR 当作不兼容的分界：`^0.8.0` 只接受 0.8.x。

## 决定

1. 1.0.0 之前：
   - 升级要求用户动手时升 MINOR（0.y.0 → 0.(y+1).0）：删掉或改名的命令、参数、MCP 工具或字段；已有输出的含义变了；旧配置失效；宿主或 Lead 必须改做法的行为变化。这类版本附"升级须知"。
   - 其余向后兼容的改动升 PATCH（0.y.z → 0.y.(z+1)）：新增命令、参数、字段或枚举值，修复，文档。
   - 同一版里两类都有，按要动手的算。
2. 每次发版（不分 MINOR、PATCH）一份 `docs/changelog-<date>-vX.Y.Z.md` 快照，记范围与门槛证据，只追加不回改。README 的版本徽章链到当前版本的快照。
3. 1.0.0 及以后按 0038 第 1 条。
4. 已发布的 tag 不改号。

## 后果

- `docs/milestone-discipline.md` §9 的改号、快照与豁免落点三步随本决定改；README 版本守卫把快照链接钉到完整版本号。
- v0.8.0 之后的改动都向后兼容（新参数、新诊断码 `overloaded`、控制面自动附加的只读执行合同），按本决定发 v0.8.1。
