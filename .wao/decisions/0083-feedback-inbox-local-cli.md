# 0083 宿主 Lead 的 WAO 反馈进本机收件箱：CLI 入口，位置锚在主检出

- 日期：2026-10-16
- 状态：accepted（Owner 2026-10-15 同意用本机收件箱、不用 GitHub Issues："嗯，同意你的判断"；其余取舍由 Lead 定）
- 来源：TD-303；决定 0049 的 2026-10-15 修订里 Owner 的第二条初心：每个项目的 Lead 用 WAO 时发现的不足，都要能送到 WAO 的开发 Lead。
- 会审：任务书预审 consult_202610160349599684y4oua（sol、kimi，两席都要求收件箱锚到主检出）；交付会审 consult_202610160439409922fzjja（sol、kimi），Lead 修正后两轮单席复核 consult_20261016045405249c31x1s、consult_20261016045843369bqw58x（sol）。

## 背景

- 宿主 Lead 发现 WAO 的问题，只能写进宿主自己的仓库，靠 Owner 转告。2026-10-15 有一份宿主反馈几小时后才被看到。
- WAO 仓库是公开的，宿主项目的名字、路径与业务内容不能离开本机。

## 决定

1. **通道是本机收件箱。**
   - 位置：`<主检出>/.wao/inbox/`，下分 `open/`、`closed/`，一条反馈一个 JSON；`ids/` 登记分出去过的每个 id，永不删除，id 不会复用。
   - 收件箱不进 git：`.wao/*` 已被忽略，另有守卫检查其中没有被跟踪的文件。
2. **入口是 CLI `wao feedback submit|list|show|close`。**宿主 Lead 都有 shell。开发机上用全局 `wao`，第三方安装上用 `scripts/wao-cli.cmd`。
3. **收件箱的位置从 WAO 代码所在仓库的主检出算出，不看调用者的 cwd。**任何入口、任何工作树，都落到同一个收件箱。
4. **条目里不留可追溯的本机信息。**
   - 只记项目标签与 WAO 的提交，不记绝对路径、环境变量、主机名；
   - 标题、正文、处理说明写盘前都过脱敏器。
5. **开发侧怎么处理。**
   - WAO 开发 Lead 开工时看 `wao feedback list`（`AGENTS.md`）；有未处理条目时，`npm run hygiene` 多一行提示。这行提示不是检查项，不改变判定。
   - 每条反馈要么进台账，要么 `close` 并写明理由。转写进公开仓库的内容，不带宿主的名字与路径。

## 否决的方案

- **GitHub Issues / PR**：仓库公开，宿主信息会公开；流程重，时间与 token 成本高。Owner 2026-10-15 同意不用。
- **新增 MCP 工具**：工具面有冻结线，扩面要 Owner 批准；宿主 Lead 都有 shell，CLI 够用。
- **收件箱跟着 cwd 或 `WAO_INSTALL_ROOT` 走**：`scripts/wao-cli.cmd` 不注入安装根，宿主调用会把反馈写进宿主仓；在开发工作树里会读到一个假空的收件箱。

## 已知局限

- 只有 MCP、没有 shell 的宿主用不了这个入口。
- 项目标签含宿主仓的目录名。它只在本机用，不是匿名标识。
- 开发 Lead 用云端模型读条目时，内容会进该模型方。这与把项目内容交给所选车道是同一性质，见 TD-266 的裁定。
- 条目用"写满临时文件再硬链接"发布，收件箱所在的卷要支持硬链接。NTFS 支持；FAT/exFAT 不支持，submit 与 close 会直接报错。
