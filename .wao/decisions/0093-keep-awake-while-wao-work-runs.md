## 背景

- 这台笔记本用电池时，屏幕空闲约 3–5 分钟就进新型待机；拉各斯常停电，插着电也会换到电池。待机里 worker、全量测试和交付验证都被冻住，醒来后被判错：
  - 10-17：5 次 glm-pro 以 `zcode turn stalled` 收尾，worker 的本地命令在待机里不动，醒着时同一条命令 145 秒跑完；
  - 同日全量测试的 filesystem 波在待机里跑了 2136 秒，撞 30 分钟看门狗，整波判失败；
  - 待机里 deepseek-acp 握手超时 19 次，kimi serve 的登录刷新连不上。
- 此后每批全量都要 Lead 手动起一个调 `SetThreadExecutionState` 的 PowerShell 进程撑着屏幕。这是手动步骤，宿主项目的 Lead 不会知道要做；10-29 它还因为占着工作目录挡住了两次删工作树。

## 决定

1. **机制**（`src/keepAwake.js`）：起一个隐藏的 Windows PowerShell 子进程，调 `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED | ES_DISPLAY_REQUIRED)`，然后等启动它的 WAO 进程退出。申请随这个子进程的线程失效：WAO 崩溃、被杀，申请都跟着消失。同一进程里的持有者共用一个子进程，最后一个释放时结束它。
   - 这是程序级的电源请求，和视频播放器防止灭屏同一种，不改任何电源设置，不需要提权。
   - 子进程的工作目录固定在系统目录，环境只带系统路径与临时目录，不带凭据。
2. **三处持有**：
   - `RunManager.waitForCompletion`：前台运行、后台 runner 与 daemon 都经它驱动，覆盖 worker 运行的整个驱动期，包括其中的打包与交付验证；
   - `runVerificationCommand`：run 外的复验、重打包与 `runs verify-commit` 也走它；
   - canonical 全量入口：整个套件期间。
3. **关闭**：环境变量 `WAO_KEEP_AWAKE=0`。两个测试入口给测试子进程设了它，测试里构造的运行与验证命令不起子进程。非 Windows 不做任何事。
4. **尽力而为**：子进程起不来（策略禁止 PowerShell 等）就不保持，绝不影响运行。

## 否决的备选

- **改电源设置**（屏幕或睡眠超时、合盖动作）：那是 Owner 的系统设置，要么要提权，要么会在 WAO 不跑时也生效。
- **只在全量与验证时保持，worker 不管**：worker 运行正是 TD-312 的受害面。原先担心笔记本装进包里一直醒着发热，Owner 说明跑任务时不装包。
- **只在用电池时保持**：电源会在运行中途切换（停电），按开始时的电源判断会漏。
- **全机一个常驻持有者加租约文件**：比按进程起子进程多出租约、陈旧清理与并发启动三类问题；现在的做法靠进程生命周期自动收尾。
- **留给 Lead 手动起**：就是现状的摩擦。

## 已知边界

- 用户自己选"睡眠"或按电源键，照样会睡；醒来后的误判仍按现有规则由 Lead 看事实处理。
- 运行期间屏幕不会因空闲而灭，合盖也不进待机；用电池时一次全量约多耗 6% 电量（10-27/28 实测）。
  - 合盖实测（10-29）：持有期间合盖 5 分 23 秒，插着电，其间停电 84 秒。没有 Kernel-Power 506，每秒一拍的探针从未中断、算力不降，内屏照常关闭。整夜合盖与长时间用电池还没测。
  - 不持有时合盖照样进新型待机：这台机器的合盖动作在两种电源下都设为不采取操作，10-18 至 10-26 仍有 15 次以 Lid 为由进入。
- 每个持有进程多一个 Windows PowerShell 子进程；同时跑多条运行就有多个，各自随进程退出。
- 只在三处持有：在这三处之外跑的长命令（例如手动起的 `npm run reliability` 里不经 `waitForCompletion` 的步骤）不覆盖。
