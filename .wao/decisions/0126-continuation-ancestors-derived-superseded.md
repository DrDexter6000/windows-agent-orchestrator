# 0126 采纳了续修谱系的后代，祖先由谱系派生为“被取代”，不再逐条拒收

- 日期：2026-11-20
- 状态：accepted
- 来源：
  - TD-353：一条续修谱系收尾，要 Lead 采纳最终 run、再给每个被续修取代的父辈逐条记拒收，然后另做回收。
  - Owner 2026-11-19 批准改为派生。
  - 方案会审 `consult_202611191333556054m2sij`（sol、kimi）；交付会审 `consult_20261119204944833sapb1x`（sol、opus）；复核七轮，从 `consult_2026111922470456185hzuo`（sol、opus）到 `consult_20261120055845435ysw26n`（sol）。
  - 第 120 批（deepseek-flash 写，七轮续修）。
- 关系：收口判定沿用决定 0095；父边检查与 `runs delivery review --since-parent`（决定 0116）共用一份；`runs lineage-close`（放弃整条谱系）不变。

## 决定

1. **派生，不写事件。** 运行 X 同时满足以下五条，就判为被后代 D 取代：
   - X 有已打包的交付；
   - X 自己没有裁决；
   - X 自己已收口（`determineRunSettlement` 为 settled）；
   - 谱系没有关闭；
   - 沿已证明的父边往下，有后代 D 带合法的采纳（交付事实通过完整校验；拒收沿用按事件类型算的旧口径，是兼容例外）。

   读面给出派生字段 `supersededByRunId`，`acceptance` 仍是 `pending`。
2. **父边只认已证明的续修事实。** 子运行转录里第一条事件是 runId 绑定的 `run.background_submitted`，带 `continuation:true` 与 `parentRunId`，且只有这一条。复用槽的 `priorRunId` 不算父边。
3. **从 X 到 D，路径上每个节点都要沿父边连回声明的根。** 以下情况整条谱系不推导，保持待裁决：
   - 中间缺父、成环（同根旁支的环也算）、自称别的根；
   - 一个转录里有互相矛盾的根；
   - 任一成员有内容不同的副本；
   - 转录枚举不完整（项目桶或归档有读不出的部分）；
   - 任一转录读不出或为空。

   兄弟不传染；末代被拒收不上传；多个合格后代取最近的，同距按 runId 字典序取第一个。
4. **优先级**：自身裁决 > 谱系关闭 > 派生被取代 > 待裁决。
5. **消费方**：
   - `lead_preflight` 不再催被取代的运行裁决，它们计入回收行。
   - nextStep 新增情形 `delivery_superseded`。
   - CLI `runs delivery --format json` 给出字段，文本多一行。
   - MCP `run_delivery` 不改 schema，只在 `nextStep` 里点名 D。
   - D 过的门与 X 相同：MCP 与 `runs delivery review` 用核验 X 的同一个授权根核验 D；本地 CLI `runs delivery`、`runs wait` 不核验 X，也不核验 D；未绑定的 MCP 查询不派生。
   - `wao worktree reclaim` 只撤 `delivery_packaged_undecided` 这一个阻塞，而且对树的每个成员都成立：
     - 计划：凡是转录可读、有打包事实的成员（孪生副本任一份有打包事实也算），都必须已合法裁决、谱系已关闭或被取代，否则整棵树连同共用它的成员一起保留；这道门在嵌套保护之前。转录枚举不完整时，整份计划不出任何删除项。
     - 执行：按磁盘现状重证全部已打包成员，删分支前也确认运行已终态。刷新时严格重新枚举，新文件与大小或修改时间变了的旧文件重新预筛；枚举失败、转录为空、读不出或副本冲突都跳过，各记各的原因。
6. **性能**：只在派生路径做字节预筛——先读原文，看是否含根 runId，只解析候选。
   - 一次请求只扫一遍库，只给真会推导的运行（有谱系引用、已打包、未裁决、已收口）收根；普通运行的读面不枚举、不预筛。
   - 不按 runId 的时间前缀排除：runId 用墙上时钟生成，不单调。
   - 前提：WAO 写的转录里 runId 原样出现、转录只追加；刷新靠大小与修改时间判断变化，同尺寸同时间的改写看不到。伪造转录不在防范范围。

## 不采纳

- **显式“谱系裁决”命令**（TD-353 原方案）：多一个写面和一套部分失败重入，派生已经覆盖它的用途。
- **按 runId 时间前缀预筛**：sol 给了反例，筛掉一个环成员，会把“不推导”翻成“被取代”。

## 影响

- 采纳最终候选之后，父辈不用再逐条拒收，回收可以直接摘掉它们的树。已有的拒收记录照旧有效（自身裁决优先）。
- 与本谱系无关的撕裂转录，不再让整库停推。
- 回收比以前更严：只靠路径声明的成员、内容冲突的孪生、空转录的分支、存储读不全时的整份计划、执行时仍在跑的分支，以前可能放行删除，现在保留或跳过。
- 理论上，很早的旧格式采纳若缺完整交付事实，会被当成未裁决，结果只会更保守；四个仓库实测没有一个运行因此变化。
- 真实库（约 5,800 个转录）实测：
  - 单次推导 0.05–0.6 秒，峰值堆 18–42 MB；全库 826 个谱系成员中 25 个被取代；
  - preflight 待办收集约 1 秒，旧代码约 0.3 秒，多出的是一条真谱系根的一次全库预筛；
  - 反事实比对删掉 121 条历史拒收再推导：100 条一致，0 条不一致；
  - 回收计划在四个仓库上新旧对比：只有 5 个被取代的祖先离开“待裁决”，没有运行变得更保守。
  - 回收执行每删一条要刷新一次：有谱系要重证时约 0.4–0.9 秒，没有时约 0.03–0.07 秒。
